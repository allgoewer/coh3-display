# CoH3 Display

Shows your opponents in the current Company of Heroes 3 match (name, faction, ELO, record)
on a small OLED driven by an ESP32-C6.

- **PC app** (this folder): a Windows tray app that follows the game's `warnings.log`, looks
  the players up on Relic's leaderboards and feeds the display over USB or WiFi. It also
  installs and updates the display's firmware and sets up its WiFi.
- **Firmware** (`firmware/`): embassy on a Seeed XIAO ESP32-C6 with an SSD1306 (128x64) on
  D4 (SDA) and D5 (SCL).
- The wire format between the two is in [PROTOCOL.md](PROTOCOL.md).

The tray menu and the installer are in German when that is the Windows display language and
in English otherwise; `--lang en` or `--lang de` overrides this for one run. The log file and
the command line are always English.

Once at each start the app asks GitHub whether a newer release exists. If so, the tray menu
gets an entry that opens the download page; the app never downloads or installs anything
by itself.

Maps are shown under the game's own titles, in the same language. The game's log only names
the scenario file, so the titles come from a table in the app, [`src/maps.tsv`](src/maps.tsv),
generated from the data the [COH Stats](https://github.com/cohstats/coh3-data) project
extracts from the game (MIT licence). After a patch that adds maps, refresh it with
`cargo run --example update_maps`; until then a new map shows under its file name.

## Building

Needs Rust (stable, with the `riscv32imac-unknown-none-elf` target; the toolchain files pull
it in) and, for the installer, [Inno Setup 6](https://jrsoftware.org/isinfo.php).

```powershell
cargo test --workspace     # the tests of the app and of the protocol it shares with the firmware
installer\build.ps1        # firmware, app and target\installer\coh3-display-<version>-setup.exe
```

The app embeds the firmware it finds at build time, so `installer\build.ps1` builds the
firmware first. A plain `cargo build` works without it; that build just cannot install firmware.

## Continuous integration

[`.github/workflows/build.yml`](.github/workflows/build.yml) builds on Windows whenever a tag
is pushed, and can be started by hand from the Actions tab.

| Tag | What happens |
|---|---|
| any tag (`test-1`, `nightly`, ...) | tests, full build; installer, exe and `SHA256SUMS.txt` are attached to the run as an artifact |
| `v` + semantic version (`v1.2.3`) | the same, plus a GitHub release with those files and generated release notes |
| ... with a pre-release part (`v1.2.3-rc.1`) | the release is marked as a pre-release |

### Cutting a release

1. Set `version` in `Cargo.toml` (and run `cargo build` once so `Cargo.lock` follows).
2. Commit: `git commit -am "chore(release): 1.2.3"`
3. Tag that commit and push both:

   ```bash
   git tag v1.2.3
   git push origin main v1.2.3
   ```

The release fails early if the tag and `Cargo.toml` disagree. The firmware has its own
version in `firmware/Cargo.toml`; bump it whenever the firmware changes, since that is what
makes the app offer (or automatically install) the update.

### Commit messages

Release notes are generated by [git-cliff](https://git-cliff.org) ([`cliff.toml`](cliff.toml))
from [conventional commits](https://www.conventionalcommits.org):

```
feat(tray): add a toggle for automatic firmware updates
fix(firmware): show the status screen after a WiFi change
feat(protocol)!: send losses and streak with every player
```

| Prefix | Section in the notes |
|---|---|
| `feat` | Features |
| `fix` | Fixes |
| `perf` | Performance |
| `docs` | Documentation |
| `refactor`, `test`, `build`, `ci`, `chore`, `style`, `revert` | Internal |
| anything else | Other |

A `!` after the type or scope, or a `BREAKING CHANGE:` footer, also lists the commit under
"Breaking changes". The scope in brackets is optional and shown in bold. `chore(release)`
commits are left out.

To preview the notes for what is not released yet: `git-cliff --unreleased`.
